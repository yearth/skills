# 任务交接

只传递接收方无法低成本、安全恢复的上下文。

## 核心原则

优先继续当前任务或会话，利用可恢复的历史。交接需要先选择继续工作的方式，再整理必要上下文，不自动生成 `.agent/handoff.md`。

## 选择续作方式

### 继续当前任务

当前任务仍可用且历史包含必要信息时，默认直接继续，不额外生成启动说明或文件。用户要求恢复之前的工作时，若环境支持任务协调，先定位或读取指定任务，再核验仓库和外部系统的实时状态。

### 新开任务或会话

参考[启动说明模板](references/continuation-brief-template.md)准备精简上下文。仅在用户明确要求时创建、fork 或分派新任务。按当前环境实际具备的能力选择交付方式：

- **有原生任务或会话工具**：按用户要求创建、fork 或发送启动说明，遵循工具当前的接口约定及项目、worktree 规则。fork 已携带相关历史时，只补充缺失的续作上下文。
- **有 Codex 任务工具**：优先使用原生创建、fork、发送工具处理用户可持续访问的任务，不用子 Agent 冒充新任务。
- **没有合适的原生工具**：提供独立完整、可复制的启动说明，供用户粘贴到目标环境。明确说明尚未创建会话，不编造工具调用或 shell 命令。仅在满足下文持久化条件时写文件。

根据工具实际结果区分：任务已创建、创建仍在排队、说明已发送、仅准备了说明。创建或发送失败、结果不确定时，能查状态就先核验再重试；无法核验则交付启动说明，并说明未确认的部分。

准备说明前，按需检查相关实时状态：准确的仓库和 worktree、分支、HEAD、领先或落后情况、未提交修改、验证结果、阻碍和授权边界。说明应包含：

- 目标结果和验收标准。
- 准确范围及当前工作副本。
- 已完成工作和证据，避免接收方重复执行。
- 必须保留的未提交修改或用户所有的状态。
- 会影响下一步的决策和约束。
- 最先读取的文件、第一条安全命令和下一项具体行动。
- 授权边界，尤其是 commit、push、PR、部署、发布及其他外部写入。
- 容易变化、需要重新查询的事实。

启动说明应独立完整且简短。不要复制聊天流水、通用项目背景，或能直接从版本控制和现有文档恢复的信息。

### 持久化恢复材料

仅在用户明确要求文件、需要跨工具交接、原任务无法可靠恢复，或长期中断需要恢复依据时，写项目内交接文档。采用最近的项目根目录和[持久化交接模板](references/handoff-template.md)；已有项目约定时沿用，否则默认 `.agent/handoff.md`。

大量支撑材料应按用途存放，不塞进交接正文：

- `repro/`：可复现输入、trace、fixture 和运行证据。
- 项目研究目录：有来源、重新调查成本较高的结论或比较。
- 测试、源码文档或决策记录：需要长期保存的产品行为和已确定决策。

接收方能低成本重新查询，或当前任务已保存的信息，不额外生成中间文件。

## 实时核验与状态保护

- Git 状态、远端状态、检查和审查结果、运行进程、端口、凭证及授权都属于实时事实，接收任务需要核验。
- 未知路径和结果明确标为未知，不编造命令、文件、分支或验证结论。
- 交接传递上下文，不产生额外授权；不能仅凭交接执行 commit、push、PR、部署、发布、发送消息或其他写入。
- 明确标记并保留用户的未提交状态。
- 更新持久化交接文件时替换过时内容，不追加工作日记。

## 质量标准

接收任务应能在两分钟内看清：

- 用户要达成什么？
- 已经完成了什么？
- 哪个工作副本和哪些文件重要？
- 下一步做什么？
- 哪些状态必须保留？
- 哪些事实需要实时核验？

选择能够回答这些问题的最轻交接方式。
