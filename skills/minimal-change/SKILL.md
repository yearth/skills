# Minimal Change

完整满足用户目标及相关既有约定，优先选择行为影响范围小、逻辑直接、容易验证的方案。行数和文件数量只是参考，不单独决定改动是否最小。

## 确定必要范围

- 根据用户目标、问题证据和现有代码确定边界。用户不必逐项点名完成任务所需的调用方调整、类型修改或验证工作。
- 沿相关证据链调查，直到能够解释问题、确定修改位置，并判断影响范围。阅读范围可以大于修改范围；没有新的相关疑点时，不继续扩展调查。
- 能从代码或环境查明的事实先查。影响目标、兼容承诺或授权范围的未决选择交给用户；可逆的小实现选择按现有约定处理，不因细节不明确就停下。

## 选择改法

- 先判断方案能否完整解决问题、保留相关既有行为，再比较影响哪些调用方和接口、增加哪些概念与依赖，以及是否容易验证。在这些条件相当时，优先更小、更直接的 diff。
- 修复已确定的问题机制，覆盖任务范围内受影响的路径；不要仅让当前例子通过，也不要自动扩展成全库同类问题治理。
- 沿用适用的现有模式和抽象。结构调整应能说明它解决了本次任务的什么具体阻碍；仅仅更整洁或可能方便未来开发，不足以纳入本次修改。是否保留重复取决于实际变化关系，不按重复次数决定。
- 不混入无关格式化、重命名、依赖升级或清理。不为假想需求增加配置、接口和兼容层；防御处理依据实际输入边界与失败路径决定。

## 检查完整性与多余改动

按逻辑改动检查 diff，既查漏项，也查无关扩张：

- 每组修改是否支持任务结果、相关兼容性或必要验证？能否移除而不损害这些目标？
- 是否为了缩小 diff 留下已知漏修、改变无关调用方行为，或引入难以维护的特例？
- 验证是否覆盖关键行为及合理的回归风险？按实际风险选择检查，不机械增减测试数量。

现有审批规则继续适用，本 Skill 不新增审批环节。确需超出已授权范围时说明具体原因；无关发现不自动纳入修改，只在明确且值得用户处理时简短提及。

交付说明改了什么、验证了什么，以及影响结论的限制。细节随任务复杂度调整，不要求固定的 follow-up 栏目。
